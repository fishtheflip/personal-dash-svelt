# Svelte Learning: путь создания Northstar

Этот файл описывает путь от пустой папки до работающего планировщика целей на
Svelte. Он также служит учебной картой проекта: что уже сделано, как это
работает и куда двигаться дальше.

## 1. Идея проекта

Northstar — это планировщик целей с дашбордом и канбан-доской.

Основные возможности текущего MVP:

- обзор общего прогресса;
- цели в колонках `Запланировано`, `В работе`, `Готово`;
- поиск целей;
- смена статуса цели кликом по карточке;
- импорт целей из Markdown-файла;
- автоматическое определение пространства, приоритета и срока.

## 2. Выбранный стек

- **Svelte 5** — реактивный пользовательский интерфейс;
- **SvelteKit** — структура приложения, маршруты и сборка;
- **TypeScript** — типизация данных;
- **Tailwind CSS 4** — стили и адаптивная верстка;
- **Lucide Svelte** — иконки;
- **Vite** — локальный сервер и production-сборка.

## 3. Создание проекта

Проект был создан в пустой папке вручную.

Главные конфигурационные файлы:

- `package.json` — зависимости и команды;
- `svelte.config.js` — настройки SvelteKit;

- `src/routes/+layout.svelte` — общий layout;

## 4. Как устроены данные

Типы находятся в `src/lib/types.ts`.

```ts
export type Status = 'backlog' | 'progress' | 'done';
export type Priority = 'high' | 'medium' | 'low';

export interface Goal {
  id: number;
  title: string;
  area: string;
  status: Status;
  priority: Priority;
  due?: string;
  progress: number;
}
```

Каждая цель содержит:

- уникальный `id`;
- название;
- пространство или область;
- статус на канбан-доске;
- приоритет;
- необязательный срок;
- процент прогресса.

## 5. Основы Svelte на примере проекта

### Компонент

Файл `+page.svelte` состоит из трех логических частей:

```svelte
<script lang="ts">
  // данные и логика
</script>

<!-- HTML-разметка -->

<style>
  /* локальные стили, если нужны */
</style>
```

В проекте большая часть стилей задается классами Tailwind, поэтому отдельный
блок `<style>` главному экрану пока не нужен.

### Реактивное состояние

В Svelte 5 состояние создается через `$state`:

```ts
let query = $state('');
let goals = $state<Goal[]>([]);
```

После изменения `query` или `goals` интерфейс автоматически обновляется.

### Производные данные

`$derived` вычисляет значение на основе другого состояния:

```ts
let filtered = $derived(
  goals.filter((goal) =>
    `${goal.title} ${goal.area}`.toLowerCase().includes(query.toLowerCase())
  )
);
```

Когда меняются цели или поисковый запрос, список `filtered` пересчитывается.

### Вывод списков

Цели и колонки выводятся через `{#each}`:

```svelte
{#each columns as column}
  <h2>{column.label}</h2>
{/each}
```

### Условия

Условный вывод создается через `{#if}`:

```svelte
{#if goal.status === 'done'}
  <span>Готово</span>
{:else}
  <span>{goal.progress}%</span>
{/if}
```

### События

Клик по карточке вызывает функцию смены статуса:

```svelte
<button onclick={() => advance(goal)}>
  {goal.title}
</button>
```

## 6. Как работает канбан

В приложении есть три статуса:

```ts
backlog -> progress -> done -> backlog
```

Функция `advance` переводит цель на следующий этап:

```ts
function advance(goal: Goal) {
  const next = {
    backlog: 'progress',
    progress: 'done',
    done: 'backlog'
  };

  goal.status = next[goal.status];
}
```

После изменения статуса Svelte автоматически переносит карточку в нужную
колонку, потому что каждая колонка фильтрует общий массив целей.

## 7. Как работает импорт Markdown

Парсер находится в `src/lib/markdown.ts`.

Пример поддерживаемого файла:

```md
# Изучение Svelte

- [ ] Пройти интерактивный tutorial !high @due(2026-06-10)
- [ ] Создать первый компонент !medium
- [x] Установить зависимости !low

# Развитие проекта

- [ ] Добавить базу данных !high @due(2026-06-20)
- [ ] Реализовать drag and drop !medium
```

Правила импорта:

- заголовок `#` становится пространством цели;
- `- [ ]` создает запланированную цель;
- `- [x]` создает выполненную цель;
- `!high`, `!medium`, `!low` задают приоритет;
- `@due(YYYY-MM-DD)` задает срок.

Файл читается в браузере:

```ts
const file = input.files?.[0];
const markdown = await file.text();
const goals = parseMarkdown(markdown);
```

Сервер для импорта не требуется.

## 8. Путь обучения Svelte

### Этап 1. Освоить текущий MVP

- изучить структуру `+page.svelte`;
- изменить стартовые цели;
- добавить новый статус;
- изменить цвета приоритетов;
- добавить новый показатель на дашборд.

### Этап 2. Разделить интерфейс на компоненты

Создать компоненты:

```text
src/lib/components/
  Sidebar.svelte
  Header.svelte
  StatCard.svelte
  KanbanBoard.svelte
  KanbanColumn.svelte
  GoalCard.svelte
  GoalModal.svelte
```

На этом этапе нужно изучить:

- `$props`;
- передачу функций между компонентами;
- snippets;
- переиспользуемые компоненты.

### Этап 3. Добавить формы

Реализовать создание и редактирование целей:

- модальное окно;
- название и описание;
- пространство;
- срок;
- приоритет;
- подзадачи.

На этом этапе изучить:

- `bind:value`;
- валидацию;
- обработку submit;
- управление формами.

### Этап 4. Добавить drag and drop — выполнено

Карточки должны перемещаться между колонками мышкой.

Реализован нативный Drag and Drop API. При переносе обновляется `goal.status`,
подсвечивается целевая колонка, а результат сохраняется локально.

### Этап 5. Сохранять данные — частично выполнено

Канбан и календарные заметки сохраняются в `localStorage`. Следующий шаг —
перейти на серверное хранилище.

Варианты развития:

- SvelteKit API routes;
- SQLite;
- PostgreSQL;
- Supabase;
- авторизация и отдельные пространства пользователей.

### Этап 6. Сделать Markdown двусторонним

Сейчас приложение только импортирует Markdown.

Следующие возможности:

- экспорт доски обратно в `.md`;
- синхронизация одного файла;
- обновление целей после изменения Markdown;
- поддержка frontmatter;
- вложенные цели и подзадачи.

## 9. Следующий практический спринт

Рекомендуемый порядок ближайшей разработки:

1. Разделить большие страницы на небольшие компоненты.
2. Добавить редактирование и удаление целей.
3. Реализовать экспорт целей в Markdown.
4. Добавить страницу конкретной цели.
5. Связать цели с датами календаря.
6. Подключить базу данных и авторизацию.

После прохождения этого маршрута нужно уметь:

- создавать приложения на SvelteKit;
- управлять реактивным состоянием;

### Шаг 1. Создан первый MVP

### Шаг 10. Разделены пространства и приоритеты

Приоритеты возвращены к старой простой модели:

- `high`;
- `medium`;
- `low`.

Рабочие направления вынесены в пространства:

- Разработка;
- Обучение;
- Личные;
- Breaking;
- Art.

Добавлена функция создания нового пространства прямо в форме новой задачи.
Пользовательские пространства сохраняются в `localStorage`, а старые сохранённые
задачи мигрируют без сброса данных:

- старые пространства `DP Testing` и `Багфиксы` переводятся в `Разработка`;
- старые пространства `Брейк` и `Творчество` переводятся в `Breaking` и `Art`;
- временные значения приоритета вроде `Разработка`, `Обучение`, `Брейк`
  возвращаются к `high`, `medium`, `low`.

Изучено:

- миграция старых локальных данных без сброса пользовательского состояния;
- хранение отдельной пользовательской коллекции настроек;
- динамическое построение вариантов Flowbite `Select`;
- почему важно не смешивать категории работы и срочность/важность.

### Шаг 11. Подключена база данных Supabase

Локальное хранение заменено на полноценный backend:

- добавлены таблицы `goals`, `spaces`, `calendar_notes`, `useful_links`;
- каждая запись привязана к пользователю через `owner_id`;
- включён Row Level Security, поэтому данные доступны только владельцу;
- добавлен вход через Supabase Auth;
- канбан, календарь и ссылки используют общий CRUD-слой `src/lib/data.ts`;
- при первом входе данные из `localStorage` импортируются в пустые таблицы;
- добавлены состояния загрузки и понятные сообщения об ошибках;
- SQL-схема хранится как миграция в `supabase/migrations`;
- ключи подключаются через `.env`, а `service_role` key фронтенду не нужен.

Изучено:

- разница между публичным anon key и секретным service-role key;
- защита пользовательских данных с помощью RLS policies;
- работа Supabase Auth в SvelteKit;
- оптимистичное обновление интерфейса с откатом при ошибке;
- организация единого data-layer вместо запросов внутри каждого компонента.

### Шаг 12. Подготовлен деплой на GitHub Pages

Проект переведён на статическую production-сборку:

- `adapter-auto` заменён на `adapter-static`;
- production base path настроен как `/personal-dash-svelt`;
- внутренние ссылки учитывают base path через `$app/paths`;
- добавлен GitHub Actions workflow для проверки, сборки и публикации;
- Supabase URL и publishable key передаются через GitHub Actions secrets;
- добавлена инструкция настройки GitHub Pages и Supabase redirect URLs.

Изучено:

- отличие локального корневого URL от GitHub Pages project URL;
- зачем статическому сайту нужен base path;
- автоматический деплой через GitHub Actions;
- безопасная передача переменных окружения во время CI-сборки.
